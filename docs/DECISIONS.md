# Decisions and deviations

Every agreed deviation from docs/blueprint.md, and every interpretation where the sources were silent, with its reason.
The requirements PDF (docs/source/OOP_S1_2026-2027_Project.pdf) wins every conflict.

|---|---|---|---|---|
| D-001 | 3 Nov | Each phase runs in a fresh cloud session on the `claude/*` branch that session is given, cut from main after the previous phase PR merges. P0 uses `claude/funny-fermi-bjxlhr`. AGENTS.md updated to match. | A cloud session may push only to its assigned branch; fresh sessions also keep context (usage) small. | AGENTS.md sessions |
| D-002 | 3 Nov | SmartStrategy's required skills S_r = the category's required skill ∪ the service's optional `required_skill_id` (one extra column on `services`; still 18 tables). | §3 gives a category one skill, but §5.3's "2/2 skills" needs a set. | §3, §5.3, §9 |
| D-003 | 3 Nov | The SLA monitor ticks every 30 s of *clock* time; under AcceleratedClock ×10 it runs every 3 real seconds. | So P1 escalation at 5/10/15 min shows at 30/60/90 real seconds in the demo. | §5.2, §5.5, §14 |
| D-004 | 3 Nov | "Team Lead" is the lead of the assignee's team; for an unassigned incident, the lead of the team best covering S_r, else the Service Desk team. | The blueprint does not say which Team Lead. | §5.3, §5.5 |
| D-005 | 3 Nov | A confirmed duplicate's reporter is "subscribed to the parent" through the cancelled child's `parent_id`; no subscription table. | Keeps the 18-table schema. | §6.2, §9 |

| D-007 | 3 Nov | Added tools: import-linter (layer contracts in `make verify`), TanStack Query, openapi-typescript + openapi-fetch (generated client), a pure-Python TF-IDF, tectonic (report, locally and in CI), plantuml.jar (diagrams). | Enforce §2 mechanically; typed client; no heavy ML dependency; one TeX engine. | §2, §6.2, §12 |
| D-008 | 3 Nov | Self-registration is open to any email unless `ALLOWED_EMAIL_DOMAINS` is set; Google Sign-In always checks `hd`. | The requirements need Employee register/login; the blueprint restricts only Google sign-in. | §8 |
| D-009 | 3 Nov | A clock-control endpoint (`/dev/clock`) exists only when `APP_ENV` is `test` or `demo`. | Playwright and the demo need to move time deterministically. | §5.2, §14 |
| D-010 | 3 Nov | CI runs only on PRs, pushes to main and manual runs, cancels superseded runs, caches uv and npm. Playwright and the report build run only on PRs labelled `e2e` or `report` (added at phase end, or when the report changes) or by hand, because a `paths:` filter on pull_request events matches the whole PR diff and would re-run them on every push. `make verify` is the gate between PRs. | Private repo: 2,000 Actions minutes a month. | — |

| D-012 | 3 Nov | No CODEOWNERS file (ownership lives in docs/PLAN.md); the four lost blueprint diagrams are not redrawn (AGENTS.md restates them; P6 generates the real ones from code); one cross-platform `scripts/dev.py` instead of per-OS scripts. | Save usage; the team reviews together. | §2 |
| D-013 | 4 Nov | External-service adapters live in `backend/app/adapters/`, with the same dependency rule as `repositories/` (domain and core only). The composition root `app/main.py` is the only module that imports every layer. | §2 names no package for adapters; this keeps services free of SDKs. | §2 |
| D-014 | 4 Nov | Helper tools install from reachable mirrors: gitleaks built from proxy.golang.org, PlantUML from Maven Central, tectonic from conda-forge via micromamba (`scripts/cloud-setup.sh`). Git hooks are local (`language: system`) so pre-commit needs no hook downloads. | GitHub release downloads are blocked in the cloud sandbox. | — |
| D-015 | 4 Nov | TypeScript pinned to 5.9.3 and @playwright/test to 1.63.0. | openapi-typescript needs TS 5.x and typescript-eslint needs < 6.1; Playwright must match the browser preinstalled in cloud sessions. | §12 |
| D-016 | 3 Nov | When no SLA policy exists for a tier and priority, the global default is the Gold target for that priority (the strictest), flagged so the admin is alerted. | §5.2 says "a global default" without naming it; the strictest choice never hides a breach. | §5.2 |
| D-017 | 3 Nov | An incident's SLA clock can only be started in NEW or CLASSIFIED (retargeting is always allowed); the response result is fixed at the first acknowledgement and the resolution target at RESOLVED, so a later priority change cannot turn a met SLA into a breach. | P1 review: a clock started late would miss pauses and acknowledgements; retargeting must not rewrite history. | §5.2 |
| D-018 | 4 Nov | `incidents` stores three values derived from its SLA clock — the response deadline, the resolution deadline (excluding a pause in progress) and the at-risk moment — kept by the mapper. | §9's SLA-status filter has to run in SQL to meet the 300 ms search target, and SQLite and PostgreSQL have no shared way to do datetime arithmetic; stored moments turn the filter into indexable comparisons. The contract suite runs every SLA case against both the in-memory and the SQL implementation, so the two cannot drift. | §5.2, §9 |
| D-019 | 4 Nov | Every sign-in failure returns one identical answer — unknown email, wrong password, locked account, deactivated account — and the reason (including how long a lockout has left) goes only to the audit trail. Registration still reports a duplicate email, because a registration form cannot work otherwise. | P2 review: a message saying "locked, try again in 12 minutes" told an attacker that the address had an account, so six requests enumerated our users. §8 asks for login protection, not for telling the attacker about it. The cost is that a locked-out user is not told why, which the sign-in screen explains generally instead. | §8 |

| D-020 | 11 Nov | P3 added the admin endpoints its screens need, which the plan had listed only as frontend work: a name directory, user management, catalogue edits, the SLA grid, the assignment settings and the audit log (15 operations; the authorisation matrix covers all 60). | P2 built reads for the catalogue and nothing for users, policies, strategy or audit, so P3.4 and P3.5 had nothing to call. | §3, §8 |
| D-021 | 11 Nov | The browser calls the API under `/api` on its own origin; the Vite dev proxy and nginx strip the prefix. A separately hosted API is named by `VITE_API_URL` instead. | One origin needs no CORS locally or in Compose; the API keeps its unprefixed paths, so nothing in P2 moved. | §2 |
| D-022 | 11 Nov | The access token lives in `sessionStorage`, one per browser tab, not `localStorage`. | §14's demo shows the Employee, Technician and Admin portals side by side in one browser, which needs three sign-ins at once; a tab's token also dies with the tab. | §8, §14 |
| D-023 | 11 Nov | Every response carries `X-Server-Time` and `X-Clock-Rate` from the injected Clock, and SLA countdowns extrapolate from the latest one. `Clock` gained a `rate` (1, 0 for the fake clock, the factor when accelerated). | Deadlines are measured on the application's clock, which runs ×10 in the demo and stands still in tests; a countdown on the browser's clock would be wrong in both. | §5.2, §14 |
| D-024 | 11 Nov | Until WebSockets arrive (P4.8) open screens re-read live data every 10 seconds. | The bell, queues and SLA chips must move during the P3 dry run; P4.8 replaces the polling with pushes. | §6.4 |
| D-025 | 11 Nov | An employee's name directory lists support staff and themselves only. An administrator cannot deactivate or re-role their own account; a technician with open incidents cannot leave the support roles, and a team's lead cannot be moved or demoted while leading it. | BR-01 keeps employees from learning who else reports incidents; the other three stop a click from orphaning open work, a team, or the last way in. | §3, §8 |
| D-026 | 11 Nov | The first deployment is `render.yaml` (API as a Docker service, web as a static site calling it through `VITE_API_URL`) with `APP_ENV=demo`. With `SEED_ON_START=true` the image seeds a never-seeded database once and leaves a seeded one alone. | Render's free plan has no shell to run a seed from, and re-seeding on every start would overwrite what an admin had configured. P5.1 moves it to production settings. | §2 Deployment |
| D-027 | 11 Nov | Cut for now, to be restored only if time remains after the rest of P4 and P5: P4.13 Telegram /report chatbot, P4.12 voice input, P4.11 health map and P5.2 the Locust run. P4.9 Telegram alerts and P4.10 Google Sign-In stay in. The never-cut list is untouched. This departs from the plan's cut order, which had Google Sign-In going before the health map. | P4 and P5 were planned at six days and five remain before the freeze on 16 Nov. The team chose to keep the two integrations and drop the four items nothing else depends on. Consequences: the demo script's Workflow 1a no longer opens with a voice report, and the 300 ms search target is stated as designed-for, not measured at 10k incidents. | §6.4, §7, §14 |
| D-028 | 11 Nov | An incident nobody holds yet (NEW or CLASSIFIED with no assignee) can be seen and assigned by any Team Lead, and appears in every lead's team queue. This replaces the earlier rule, tested in P1, that only an administrator could work an unassigned incident. **Needs the team's confirmation**: it widens what a lead can see. | P3 review: §5.3 says such an incident is "queued for the Team Lead", but with no assignee it matched no team, so no lead could open it and only an administrator's search found it. D-004 names one lead to notify; letting only that lead open it would need the incident to record who it was queued for, which the schema does not. | §5.3, BR-01, BR-02 |
| D-029 | 11 Nov | Nobody creates, changes or deactivates an account whose role is above their own escalation level, so only an IT Manager manages IT Managers. Anyone signed in may read retired services and categories (`include_inactive`), flagged inactive; the report form offers only active ones. | P3 review: Administrators and IT Managers hold identical permissions, so an administrator could demote the IT Manager. Retired rows are needed to name the service of an incident reported before the retirement. | §3, §8 |

| D-030 | 12 Nov | Duplicate detection compares a report with incidents still open (NEW to ON_HOLD) reported in the last 14 days, at most the 300 newest. Gemini's vectors are stored per incident in `incident_embeddings`, tagged with provider and model; TF-IDF vectors are recomputed per check over those recent incidents and never stored. θ = 0.49 and θ-high = 0.89 come from 52 hand-labelled pairs (`scripts/tune_duplicates.py`, `docs/testing/duplicates.md`); a test fails if the constants drift from the tuning. | TF-IDF weights depend on the corpus, so a stored TF-IDF vector cannot be compared with a later one; §6.2 says "stored per incident", which holds for the embeddings that are comparable. Bounding the window keeps the check inside the 300 ms target. | §6.2, §9 |
| D-031 | 12 Nov | "Follow this instead" records the report and cancels it at once as a duplicate of the chosen incident, with the reporter as actor; only an incident the similarity check itself suggested may be followed. Any staff member who may work an incident (BR-02) may confirm it as a duplicate. A parent must exist, be open, and not itself be a duplicate, and an incident that already has duplicates cannot become one. The reporter of a linked duplicate sees the parent's id, title and status and is notified when it is resolved; they still cannot open the parent. | §6.2 does not say what following does or who confirms. Following is how an employee comes to hear about someone else's incident, so it is limited to what was already shown to them (BR-01); one level of linking keeps "subscribed to the parent" (D-005) meaningful. | §6.2, BR-01, BR-02, BR-09 |
