# Deploying I-ITSM (P3.6)

The API and the web app run on Render's free plan and PostgreSQL on Neon's; neither needs a
card. Why these two is in docs/PROGRESS.md (P2.10). `render.yaml` describes both services, and
every push to `main` redeploys them.

## One-time setup (about ten minutes)

1. **Neon.** Create a project in the region nearest Render's. Copy the connection string and
   change its scheme from `postgresql://` to `postgresql+psycopg://`, keeping `?sslmode=require`.
2. **Render.** New → Blueprint → pick this repository. Render reads `render.yaml` and asks for
   the values marked `sync: false`:

   | Service | Variable | Value |
   |---|---|---|
   | i-itsm-api | `DATABASE_URL` | the Neon string from step 1 |
   | i-itsm-api | `CORS_ORIGINS` | `["https://<web>.onrender.com"]` (a JSON list) |
   | i-itsm-api | `FRONTEND_URL` | `https://<web>.onrender.com` |
   | i-itsm-web | `VITE_API_URL` | `https://<api>.onrender.com` (no trailing slash) |

   Render names the services after `render.yaml`, so the URLs are normally
   `https://i-itsm-web.onrender.com` and `https://i-itsm-api.onrender.com`: enter those up
   front. Render adds a suffix when a name is taken; if it did, correct the values once the
   dashboard shows the real URLs and redeploy both. `JWT_SECRET` is generated by Render.

   **The API refuses to start until `CORS_ORIGINS` is right** (P5.1): with `APP_ENV=prod` it
   must be the web app's exact origin, `https://` and no trailing slash or path. Left empty, or
   wrong, the first API deploy fails its health check; fix the value and redeploy.

   **The web app does not work until that second deploy.** `VITE_API_URL` is baked in when the
   site is built, and the first build has it empty, so the first version of the site calls
   itself instead of the API and every sign-in fails. Set the variable, then use "Manual
   Deploy → Clear build cache & deploy" on i-itsm-web.
3. **First start.** The API image runs `alembic upgrade head`, then, because
   `SEED_ON_START=true`, seeds the demo data into the empty database (about a minute) and runs
   the SLA monitor over that history once, quietly, so the first live tick does not notify
   anyone about months-old breaches (P5.5). Then it serves. Later starts find the seed marker
   and change nothing, so configuration made on the admin screens survives a redeploy.

   **Production settings (P5.1).** The Blueprint sets `APP_ENV=prod`, and the API then refuses
   to start unless `JWT_SECRET` is at least 32 characters (Render generates one) and
   `CORS_ORIGINS` lists only the web app's `https://` origin. If the API's log says
   `CORS_ORIGINS must list the web app's https:// origin(s)`, the value from step 2 is missing
   or has a trailing slash or a path. HTTPS itself is Render's: both services get a
   certificate and redirect plain HTTP.

   **The demo accounts are public.** `SEED_ON_START` creates one account per role, including
   `admin@campus.edu` and `manager@campus.edu`, with the password printed in the README, so
   anyone who reads the README can administer the deployment. That is deliberate while the
   evaluators need to sign in. After the evaluation, deactivate the admin and manager demo
   accounts on the Users screen (signed in as another IT Manager), or delete the deployment.

## Checking it

- `https://<api>.onrender.com/health` answers `{"status":"ok","database":"ok"}`.
- `https://<web>.onrender.com` shows the sign-in page; the demo accounts in the README work.
- Workflow 1 by hand: sign in as the employee, report an incident, see it assigned.

## What the free plan changes

- **The API sleeps after 15 minutes without traffic** and takes about a minute to wake. While
  it sleeps the SLA monitor does not tick; the first tick afterwards catches up. Open the app a
  few minutes before a demo, or use "Run the monitor now" on the SLA violations screen.
- **Outbound SMTP is blocked**, so email falls back to the console log; in-app notifications
  are unaffected.
- **`VITE_API_URL` is baked in at build time.** Changing the API's URL means rebuilding the
  static site.

## A demo instance (P5.5, D-036)

The recording itself runs locally with `make demo-reset`. To give the deployment the same
demo state instead, change three variables on i-itsm-api and redeploy:

| Variable | Value |
|---|---|
| `APP_ENV` | `demo` (prod refuses to reset; demo also exposes `/dev/clock`, D-009) |
| `CLOCK_MODE` | `accelerated` (×10: a P1's 5-minute response window takes 30 s) |
| `DEMO_RESET_ON_START` | `true` |

Every start then wipes the database, reseeds it, catches the monitor up and stages Workflows 1
and 2. On the free plan that includes every wake from sleep, which is deliberate: the ×10
clock restarts from the real time when the process does, so data written by the previous run
would otherwise sit hours in the clock's future. Anything done on a demo instance is gone the
next time it sleeps.

**Going back to production.** The ×10 clock leaves data dated in the future, and the seed
marker stops a fresh seed, so switch back in two deploys: first set `CLOCK_MODE=system` and
keep `APP_ENV=demo` and `DEMO_RESET_ON_START=true`, so one start resets the data on the real
clock; then set `APP_ENV=prod` and delete `CLOCK_MODE` and `DEMO_RESET_ON_START`.

`make demo-reset` on a laptop wipes only a local database (SQLite, or PostgreSQL on
localhost or Compose's `postgres`); pointed at Neon it refuses. The image passes
`--allow-remote-database` only when `DEMO_RESET_ON_START=true` asks for it.

## Docker Compose instead

`docker compose up --build` runs the same API image with PostgreSQL and serves the web app
through nginx on http://localhost:8080, with `/api` proxied to the API.
